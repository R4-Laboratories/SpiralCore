## Implemented upstream path

A signed `ExecutionPlan.mailbox` grants a mailbox ID, capability-authority verifying key and execution epoch. `LaunchRequestBuilder::mailbox` carries that grant through normal signed admission. The backend must declare `guest_mailbox` support or launch refuses. The grant enables the exact guest cmdline token and dedicated port 5257, separate from FlowMux 5253 and other services. [Grant contract](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-contract/src/protocol/mailbox.rs#L167), [request API](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-client/src/launch/request.rs#L465), [backend admission](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-hostd/src/mailbox_process.rs#L158)

The workload writes `OutboxMessage` to `/run/mvm/mailbox/outbox`. Its encoding is 32 recipient bytes followed by plaintext body. The guest agent accepts one host vsock connection at a time and forwards that message. The host's per-VM `mvm-mailbox` process dials the guest port, seals/signs the plaintext with host-derived per-mailbox keys, validates its canonical envelope and queues plaintext for the host. `mvm_client::mailbox::recv(name)` takes the oldest message and signs an audit record of length and lifetime accepted/read counts before returning it. A read whose audit emission fails does not deliver the removed message. [Guest outbox](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-agentd/src/mailbox_outbox.rs#L1), [guest listener](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-agentd/src/bin/mvm-guest-agent/mailbox.rs#L1), [audited receive](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-client/src/mailbox.rs#L1)

The helper gets derived keys over stdin, clears its environment, and holds no audit-signing seed. Its lifecycle follows launcher/VM state and canonical helper cleanup. Encryption on this implemented path is host-to-host; the guest has no mailbox key or per-workload signing identity. SpiralCore can process plaintext only at this admitted endpoint, with encryption and authority still owned by canonical MVM. [Process ownership](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-hostd/src/mailbox_process.rs#L1), [host sealer](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-hostd/src/mailbox_service.rs#L72)

Launch limits are 64 queued messages and 64 KiB per frame, with five-second socket I/O bounds. The derived default capability admits 16 KiB bodies, 600 messages/minute, eight outstanding calls and 1 MiB queue contribution, with one-hour validity. The concrete local queue enforces depth and frame length; full aggregate tenant/sender/call/rate accounting must be qualified separately rather than inferred from fields present in a signed capability. [Launch bounds](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-hostd/src/mailbox_launch.rs#L243), [queue admission](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-hostd/src/mailbox_service.rs#L504)

## Remaining customer semantics

The current native path is a useful real endpoint, but issue #4629 remains open. Its default header is Call-only and uses `application/vnd.mvm.guest-message` v1. The implemented exchange returns a JSON admission verdict `Result<(), Refusal>`. It does not yet supply the complete correlated application Reply, distinct Cast API, cancellation/late-reply disposal, destination-receipt carrier, persistent retries or full per-tenant/host aggregate budget required by that issue. [Live acceptance criteria](https://github.com/tinylabscom/mvm/issues/4629), [canonical framing](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-core/src/mailbox/frame.rs#L1)

The guest claims and deletes its outbox before the host verdict, including refusal or connection failure. That is explicit source behavior. Neither lossless recovery nor an acknowledged warm cache can rely on automatic retransmission here. A return lane and retained producer identity must land before adapting the interactive SpiralCore object-v1 exchange. Exact compression of one delivered body does not prove delivery semantics. [Outbox consumption](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-agentd/src/mailbox_outbox.rs#L84)

## Compatibility and immediate implementation

The canonical envelope/signature/encryption ownership remains upstream. However, upstream lacks fork APIs used by our service adapter, including `OpenedMailboxEnvelope` and `open_verified_envelope`. `AuthorizedMailboxFrame::as_bytes()` already exists and needs no new accessor. The adapter's `live.rs:660` use of the absent `ChannelLimits::max_pending_bytes()` checks an invariant already enforced by upstream's private-field constructor, so remove that redundant consumer check. Prepared-header access is absent, but direct uses found in campaign tests can be adapted; it is not required by the production adapter send path, which verifies `prepared.envelope()` canonically. Its outbound transport authorizer admits Send only; blindly repinning would break our Reply-only-grant behavior. The fork's experimental bandwidth-profile API is also absent. Rebase a narrow API contribution rather than restoring the entire old fork. [Canonical open](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-core/src/mailbox.rs#L468), [outbound authorization](https://github.com/tinylabscom/mvm/blob/d27a20cb1a12a7c21b253a3bf6b7579925a7d1f3/crates/mvm-core/src/mailbox/transport.rs#L554)

The next source slice should expose the already canonical verified header plus payload as an unforgeable result, retaining existing `open_envelope` callers, and validate outbound Reply under the correct admitted operation. Reuse upstream's existing authorized-byte accessor and avoid adding redundant limit or prepared-header getters. Retain a prepared-header getter only if an independently justified production caller needs it. Focused RED tests cover forged header substitution, wrong epoch/revocation, Reply-only capability and opaque transport byte equality. These are upstream API additions, not a second envelope.

Then bind SpiralCore's service dispatch to the existing per-VM mailbox process and workload outbox service. Retain authenticated header metadata through admission, replace no upstream launch/key/port owner, and add an explicitly admitted correlated return operation plus producer retry identity. Use canonical receipts to distinguish admission from application completion. Test QueueFull and lost verdicts before enabling warm-cache membership acknowledgment. Reuse our aggregate budgets and receipt/replay tests as contribution requirements while implementing them under current MVM ownership.

The first native witness can immediately prove current guest-to-host exact-body transport and audited receive with the new helper. The product gate then requires bidirectional object-v1 transfer over the completed Call/Reply path, exact readbacks, actual bytes both ways, CPU/lifecycle time, saturation isolation and positive helper shutdown/reap. Keep FlowMux integration, owner access and fleet/WAN qualifications as their existing separate services and acceptance gates. Current signed-plan and canonical-envelope contributions do not authorize a guest NIC, extra egress path or shared FlowMux queue.
