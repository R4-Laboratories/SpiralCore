# Broad WAN controls: receiver policy and bounded zstd prefix profile

Reviewed 2026-10-29 at SpiralCore `d03fe1630bba787a28cc3fa3ae201c4a1a75388b`. This is the implementation contract for the next controlled experiment, not a performance result. Only the parent-authorized endpoint/client/protocol/codec changes are in scope. MVM and 64 MiB qualification remain later stages.

## Receiver policy

Add immutable `ColdGraphPolicy::{EagerBounded, Disabled}` to each Endpoint through `open_with_policy(root, limits, authority, policy)`. Existing `open` keeps `EagerBounded`, preserving existing callers and Limits struct literals. Disabled skips only the optional graph construction and reservation for Raw/Zstd publication. It does not weaken explicit DAG verification, whole-object hashing, authorization, quota scans, private cache ownership, replay rules or durable publication. Disabled cold publications have no manifest ID and cannot be discovered as DAG bases; their exact ObjectId and verified bytes remain usable by sparse and prefix modes. Existing publications are not rewritten by changing a future endpoint instance's policy.

Use Disabled for all arms of the new minimal receiver comparison (raw, ordinary zstd, sparse, zstd prefix). Retain the earlier eager-default result as a separately named reference. A peer cannot select receiver warming policy. Seeding, encoding, digest verification, receiver CPU and durable writes remain inside their existing measured boundaries. Report the actual selected mode, including sender fallback.

## Versioned conventional prefix control

Use the already pinned zstd 0.13.3 / zstd-safe 7.3.0 / zstd-sys 2.1.2 + zstd 1.5.7 implementation. The established dictionary/prefix patching mechanism is described in the [zstd project's patching overview](https://github.com/meta/zstd/wiki/Zstandard-as-a-patching-engine). This is a configured zstd prefix control, not a claim of byte-identical CLI `--patch-from` behavior, rsync, or VCDIFF. [VCDIFF](https://www.rfc-editor.org/rfc/rfc3284.html) specifies a delta format; no qualified encoder/decoder is currently installed or imported for this path.

Mode tag 4 is `ZstdPrefixV1`. Begin has target byte ObjectId and length, no manifest, and a required whole-base ObjectId. Target and verified base are each at most 16 MiB. The base is loaded and fully verified within the authorized namespace before Ready. No global dictionary or cross-tenant reuse is permitted. DescriptorId binds the existing canonical Offer bytes, including mode/base/target. Old peers reject the unknown mode.

Each Data body is `[encoding=4:u8, encoded_chunk_length:u32LE, recipe_version=1:u8, encoded_bytes]`. Chunk length is nonzero and at most 60 KiB; at most 512 Data chunks and at most `zstd compress_bound(target_len)` encoded bytes are accepted. Accepted counts cumulative encoded bytes, not output. Data validation is atomic. At Finish decode exactly one ordinary zstd frame with required declared content length equal to target length, no dictionary-ID field, an explicit checksum, and declared window at most 32 MiB. Reject trailing/concatenated/skippable frames, unknown size, malformed headers, oversize encoding, wrong output length and bad checksum. Apply the same final ObjectId check and authorization/durable-publish path as other modes. No optional DAG warming is performed for mode 4.

The sender constructs one whole prefix frame (level 3, windowLog 25, long-distance matching on, one worker thread, declared content size and checksum). It compares complete object-protocol request cost against raw before Begin and selects raw when the patch is not cheaper. There is no automatic retry or mode change after Begin. `transfer_zstd_prefix_batched(base, target, transfer_id, warm_probe, exchange)` retains the existing 16 MiB batched-object ceiling and returns the selected mode. Cost comparison includes the longer prefix Offer, Data frame headers, version bytes, and common Finish; common reply sizes cancel. Encoder work and fallback preparation are measured, not free preprocessing.

## Allocation and work contract

Admission reserves `2*target_len + 2*base_len + encoded_cap + 4 MiB decoder allowance + 2 MiB existing ledger allowance` inside the existing shared resident limit before loading base, staging the frame, or decoding. Maximum is about 86.063 MiB per admitted 16 MiB attempt, so the active-count limit is not a promise of four admissions under every resident setting. Staged encoded storage is allocated once to the checked cap; target output is allocated to the checked declared length. Control/replay accounting and existing transport scratch carve-out remain intact.

The decoder uses safe one-shot `DCtx::ref_prefix` and `decompress` with caller-owned output, not a streaming decoder. In pinned zstd 1.5.7, `ZSTD_decompressDCtx` uses the referenced raw-content prefix, `ZSTD_DCtx_refPrefix_advanced` loads it by reference and single-use, and one-shot decompression does not allocate an advertised-window-sized streaming buffer. Raw prefix DDict and DCtx allocations are fixed-size; internal block/literal tables are bounded independently of frame output. Validate frame header, encoded cap and output size before creating this context. A conservative 4 MiB reservation covers these fixed tables; `sizeof` checks are defense in depth, not the sole allocation defense. Prefix lifetime is lexically longer than the decoder. No unsafe application code or new dependency is introduced.

The sender's fixed configuration and 16 MiB input cap bound work, but a 128 MiB encoder-context estimate is not an enforced process peak-memory limit. Record any context-size qualification separately; do not turn post-allocation `sizeof` into a hard preallocation or RSS claim. Sender input/output and protocol-frame copies also consume memory. The receiver rejects over-budget input before work; sender preparation operates on local trusted bytes.

## Required checks and staged delivery

First demonstrate RED then GREEN for policy and mode behavior. Cover codec round trips, empty values, edits and insertion, invalid versions/lengths/windows/checksums/trailing frames, encoded/chunk count limits, resource admission, namespace/base corruption and absence, revocation, replay/cancel, durable reopen and client receipt validation. Verify default warming remains unchanged and explicit DAG still works when optional warming is disabled. A missing base never triggers an unannounced cold retry. All existing source/identity/wire/durability tests must remain green.

Before the broad 16 MiB campaign freeze exact source, settings, fixtures, selected modes and trial order. Insertion cases must keep target at or below 16 MiB (for example, start with `16 MiB - insertion length`); do not raise the ceiling silently. Preserve the capture-controller completeness gates and all seeding costs. Compare HTTP-body bytes, qualified per-connection IP counts, endpoint CPU and wall time separately. Do not infer energy savings from CPU alone.

64 MiB needs a separate proposal for batch sizing, encoded/base/output reservations, decoder qualification, peak-memory observations, cancellation, restart and disk exhaustion. The present changes do not authorize that expansion or a persistent quota index.

## Later MVM and small-orchestrator boundary

SpiralCore remains a generic authenticated-endpoint object protocol for this phase. Later integration must use MVM's canonical mailbox transport and an explicit vsock/mailbox bridge, preserving the envelope's cryptographic boundary; FlowMux 5253 must not be repurposed. Bridge/orchestrator addressing maps stable authenticated node identity and tenant/capability/epoch to current guest routes; a vsock CID is not an authorization identity. Define bounded queue/backpressure, rebind/restart/revocation behavior, durable idempotency and at-least-once retransmission. Distinguish object Published (verified durable object), mailbox accepted/delivered, and application processed acknowledgments. Small networks need these lifecycle contracts as well as large deployments. No MVM implementation, port assignment, FIPS validation or CUI release claim is made here.
