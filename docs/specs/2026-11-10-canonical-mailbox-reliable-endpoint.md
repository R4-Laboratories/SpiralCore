# Canonical reliable mailbox endpoint

This is an implementation contract for the next current-MVM slice of [#4629](https://github.com/tinylabscom/mvm/issues/4629), following the [current native integration](2026-11-10-current-native-mailbox-integration.md). The inspected upstream source pin is `b3b2afd8f5183b48632c6ff85c0781801d60aabf`; the four-file verified-open/Reply API patch is rebased on that source separately. The earlier `241a2fe9` inspection is historical. This document specifies proposed reliable behavior and makes no executed reliability, WAN or backend claim.

## Authority and existing entry points

Use `mvm-contract::protocol::mailbox`, `mvm-core::mailbox` and its existing frame/transport modules. Guest code belongs in `mvm-agentd::mailbox_outbox` and the original `mvm-guest-agent/mailbox.rs` listener. Host ownership belongs in the existing `mvm-hostd::mailbox_service`, `mailbox_launch` and `mailbox_process`. Expose workload and host APIs through `mvm-agentd` and `mvm-client::mailbox` respectively. Do not add an `mvmd` dependency.

Current `MailboxGrant` contains mailbox, authority key and execution epoch. `mvm.mailbox=1` asserts the existing listener on port 5257. `OutboxMessage` is exactly recipient bytes followed by a nonempty body. Ari's current `write_outbox` adds atomically published message files to `/run/mvm/mailbox/outbox`, now a spool directory with `MAX_SPOOLED_MESSAGES = 256`, supporting back-to-back writes. Its filenames sort lexicographically, and `spooled` ignores dot-prefixed temporary names. Current `forward_outbox` selects the oldest visible file and removes it before decoding/sending or receiving a verdict. Reliable retention must extend this spool rather than restore the superseded one-file producer.

The current host route is the backend-owned `HostDialRoute` carried in `mailbox_process::MailboxProcessConfig.route` and `mailbox_launch::ServePaths`; the helper dials through that route. Preserve its PortSocket/Mux selection instead of rebuilding paths in the adapter. `GuestSealer` stamps a template and a process-local counter. The host queue currently retains plaintext without its authenticated header, and its audited `recv` removes data before audit completion. Those limitations remain reliability work despite the spool improvement. [Spool change #5302](https://github.com/tinylabscom/mvm/issues/5302), [backend route #5309](https://github.com/tinylabscom/mvm/issues/5309).

The canonical envelope, capability, crypto domains and destination receipt types stay MVM-owned. The guest holds no mailbox signing or encryption key in this profile. Encryption remains host-to-host. The service version cannot promote that tier to guest-to-guest confidentiality.

`admission::mailbox_grant::at_workload_epoch` now reads the workload ledger epoch and remints that epoch's authority. Signing keys and identities are epoch-derived. Encryption uses a separate random root plus a freshly minted per-launch secret in the VM state directory, with the secret overwritten/flushed/unlinked on stop/replacement. This is logical erasure, with the filesystem caveat in the source. Preserve these owners and derivations. A signing seed does not supply the new encryption root/launch secret. [Ledger alignment #5308](https://github.com/tinylabscom/mvm/issues/5308), [key separation and launch secret #5317](https://github.com/tinylabscom/mvm/issues/5317).

The current encryption key cannot be derived by a receiving peer host from public addressing or this local framing. Its per-launch secret never leaves the sending host. Cross-host key agreement or recipient key wrapping remains an explicit missing [#4633](https://github.com/tinylabscom/mvm/issues/4633)/[#5312](https://github.com/tinylabscom/mvm/issues/5312) contract. Reliable local delivery can proceed without inventing that authority. Cross-host/WAN admission remains unavailable until canonical recipient key ownership, authenticated distribution/agreement, rotation/revocation, key IDs and retirement are implemented and tested. No adapter copies the launch secret to establish a shared key. A durable mode also needs a reviewed way to retain decryptability before shredding; ephemeral mode makes no such promise.

## Signed mode selection

Add a `Copy` contract type `MailboxLocalServiceGrant` containing `version: MailboxLocalServiceVersion` and `limits: MailboxLocalLimits`. Version `ReliableV1 = 1` is the only new recognized value. Add `MailboxGrant.local_service: Option<MailboxLocalServiceGrant>` with Serde `default` and `skip_serializing_if = "Option::is_none"`. Absence selects the exact legacy wire and kernel token. Freeze old signed-plan JSON and signature fixtures before modifying this shape. Update struct literals explicitly.

The limits contain positive checked integers for payload bytes, spooled requests, retained request/result bytes, queued host messages, active calls, local-frame bytes and retained host bytes. Initial admission ceilings are a 16 KiB body, at most the existing 256 spooled messages, one active forwarding claim, four pending Calls, eight queued host application messages and three live connections per VM. The default reliable spool byte ceiling is 1 MiB, counting complete encoded requests, results, claims and private metadata; reserve it from the configured guest storage budget. The count is a ceiling, so the byte budget may fill earlier. These are maxima within shared credits, not new allocations. `max_frame_bytes` is 65,536 including the frame body and excludes its four-byte prefix. The canonical capability can impose smaller limits. No service mode increases an existing limit implicitly.

The signed-plan validator rejects unknown versions, unsupported backend/runtime service versions, invalid limit combinations and durable requests without an implemented durable owner. Backend `guest_mailbox` alone does not establish reliable-version support. Add an explicit admitted version check to the host launcher and runtime manifest compatibility path. Preserve this admitted service/version/limits when `at_workload_epoch` remints the grant; it must neither drop opt-in fields nor retain an old authority. The original cmdline renderer emits `mvm.mailbox=1 mvm.mailbox.service=1` only for the signed reliable grant. The guest refuses duplicate, conflicting or unsupported service tokens. A reliable token requires the mailbox token. No grant means no listener or producer directory.

No magic-prefix sniffing occurs in the legacy recipient/body decoder. A version mismatch fails before consuming the reliable producer slot. A reliable host never redials in legacy mode after refusal. Existing legacy helper and guest tests freeze their original bytes and behavior.

## Local framing and connection roles

All roles use the existing host-dialed guest port 5257 and the same helper owner. The host opens at most one connection for each role. They have separate bounded queues and workers, sharing one policy and resource owner.

| Role byte | Role | Direction and work |
|---|---|---|
| 1 | Submit | Guest sends one immutable request, host returns local admission |
| 2 | Deliver | Host presents a verified inbound application value, guest accepts into its bounded inbox |
| 3 | Control | Bidirectional Query/Cancel/Retire requests and results, receipts and delivery acknowledgments |

Role 3 has reserved credits. Submit or Deliver stalls cannot occupy its socket, worker, buffer or credit. No received role authorizes access to host administrative APIs. Check the accepted vsock peer is the host CID using the existing transport boundary. Mock Unix streams are test bindings and cannot enable this production mode.

Submit and Deliver frames use the admitted maximum up to 65,536 bytes. Control frames have an additional fixed 4,096-byte maximum. The codec checks the role-specific bound before allocating the frame buffer.

The host sends a fixed 52-byte greeting before either side emits framed data. It consists of eight ASCII bytes `MVMBX001`, `u16 BE` version 1, the role byte, one zero byte, a 32-byte host-generated session binding and a nonzero `u64 BE` connection generation. The guest echoes these 52 bytes exactly. The binding names the admitted VM instance and grant generation within this local service. It is constant across the three roles and their reconnects, changes on helper restart or authority-generation replacement, and is an association value rather than an authentication credential. Reject an unknown role, nonzero reserved byte, stale generation, wrong echo or second live connection for a role. The host obtains identity from its actual launch owner, never the echo. A greeting has one original five-second I/O deadline.

Every subsequent frame is `u32 BE body_length`, then `u8 opcode`, then a fixed-format payload. Length includes the opcode. Reject zero length, length above the admitted frame maximum, unknown opcode, truncated fields, noncanonical booleans, trailing bytes and arithmetic overflow before allocation or state mutation. Integers are unsigned big-endian except explicit canonical signed absolute timestamps. Byte strings use `u32 BE length` followed by exact bytes. Fixed IDs are raw bytes. A content type uses `u8 name_length`, ASCII name and `u16 version`, validated by current `ContentType::parse`. Local fields have no JSON, executable source, pointer or native-endian encoding. Opcode 7 carries the separately specified existing canonical receipt bytes.

| Opcode | Payload |
|---|---|
| 1 Submit | originating session binding 32 bytes, `request_id:u64`, kind byte 1 Call/2 Cast/3 Reply, recipient 32 bytes, content type, `expires_at_unix_ms:i64`, `timeout_ms:u32`, correlation 32 bytes, causation 32 bytes, reply-token bytes, body bytes |
| 2 SubmitResult | request ID, semantic SHA-256 32 bytes, local disposition byte, canonical message ID 32 bytes, canonical correlation ID 32 bytes, host service generation 32 bytes |
| 3 Deliver | `delivery_sequence:u64`, canonical message ID, correlation, causation, sender and recipient (32 bytes each), kind, content type, signed expiry i64, reply-token bytes, plaintext body bytes |
| 4 DeliveryAck | delivery sequence, canonical message ID, disposition 1 inbox accepted/2 full/3 expired/4 unavailable |
| 5 ControlRequest | `control_id:u64`, operation byte 1 Query/2 Cancel/3 Retire, target request ID u64 |
| 6 ControlResult | control ID, target request ID, local disposition, canonical message/correlation IDs, service generation |
| 7 DestinationReceipt | target request ID and existing canonical `SignedDestinationReceipt` serialized through one bounded MVM-owned encoder |

Implement and freeze the receipt carrier in `mvm-core::mailbox::frame` as target request ID followed by a length-prefixed byte string containing `serde_json::to_vec` of the existing `SignedDestinationReceipt`. Cap this string at 2,048 bytes before deserialization, apply canonical bounds and verify the existing destination signature. Do not change the signed receipt serializer or signature domain. Opcode 7 is a local carrier for that value, not a new receipt signature. It creates no application Reply and requests no receipt of its own.

Submit uses only opcode 1 guest-to-host and opcode 2 host-to-guest. Deliver uses only opcode 3 host-to-guest and opcode 4 guest-to-host. Control uses opcodes 5, 6 and 7; opcode 4 may also repeat there after a Deliver reconnect. Each direction has its own nonzero increasing control IDs, scoped by the greeting generation. A ControlRequest receives exactly one matching ControlResult; a retransmission reuses its ID. Query and terminal result delivery share the reserved control bound and cannot enqueue application data. Reject a legal opcode arriving on the wrong role or direction.

New Call and Cast requests carry zero correlation and causation and an empty reply token. The host returns its allocated canonical Call correlation in SubmitResult. Reply requires the exact correlation, causation and token from the delivered Call. Canonical Call `reply_to` comes from the host's actual receive capability. Canonical Cast/Reply have no `reply_to`, preserving current message validation. A locally originated Cast uses zero correlation/causation, which current MVM bounds validation permits. Its SubmitResult correlation is zero. Every new Call uses a fresh correlation and zero causation; its Reply uses that Call's correlation and message ID as causation.

Local dispositions are explicit bytes 1 AcceptedEphemeral, 2 DuplicateEphemeral, 3 Full, 4 Backpressured, 5 Unauthorized, 6 Expired, 7 Unavailable, 8 ShuttingDown, 9 Conflict, 10 Retired, 11 Cancelled and 12 Deadline. Zero IDs in refusals mean no canonical message was admitted. They cannot be interpreted as a destination receipt. Unknown disposition values refuse. No AcceptedDurable local result exists in this initial profile.

The return token is at most 256 bytes, data-only and host-issued. It indexes one pending, authenticated canonical Call held by the original service owner. It is scoped to that VM/boot/grant generation and the exact reply capability ID, caller, destination, correlation, causation and expiry. The guest cannot submit a raw capability or choose a new authority through this field. Token knowledge alone is insufficient without that bound local owner and current authorization. Empty tokens are required for Cast and locally originated Call. Reply requires an existing token and exact matching metadata. Do not put the token into the canonical envelope.

An individual frame has one original five-second I/O deadline. Frame progress does not reset it. Application Calls use their own monotonic deadline derived once from the validated signed absolute expiry and requested timeout, whichever is earlier. Existing product deadlines remain acceptance constraints until independently changed.

## Request identity and guest retention

`GuestRequestId` is a nonzero monotonic u64, local to the actual admitted VM boot. The spool writer owner allocates it under the existing private outbox directory. Wrap refuses. Serialize counter, count/byte reservation and immutable message publication across concurrent producers. Preserve the published request across helper reconnect. VM restart is an explicit new boot/ledger epoch event and does not turn an old spool item into a new request.

Reliable mode uses the current `/run/mvm/mailbox/outbox` spool. Visible message basenames are the zero-padded 20-digit request ID, so lexicographic order is allocation order without relying on wall time. The additive typed producer API uses the same spool custody and provisioning as `write_outbox`; the signed mode selects the contents. It must support multiple back-to-back published requests, up to the existing 256-entry ceiling and the admitted byte ceiling. Legacy mode retains its current timestamp/pid/counter filenames and recipient/body encoding.

Private metadata names are `.reliable.counter`, `.reliable.scope` and `.reliable.results/`; the forwarding claim is `.reliable.claimed`. Dot-prefixed metadata cannot enter the legacy visible-message scan. Each message/claim contains exactly one encoded Submit frame including its length prefix. Each result file under the private results directory is named by the same fixed-width ID and contains exactly one encoded SubmitResult. The counter is exactly one u64 BE last-allocated ID. Under the shared writer owner, reserve count/bytes and atomically publish an incremented counter before no-replace publishing a new visible item. A crash between counter and item can leave a gap, which the host permits. Use private exclusive temporary files and existing checked filesystem/synchronization helpers. Counter zero is initially unallocated; incrementing u64::MAX refuses. Temp, claim, result and quarantined files all count toward the same retained byte bound; hidden names do not grant free space.

The scope file is the exact 32-byte nonzero binding published by the guest agent after a successful greeting. The typed producer returns Unavailable until it exists. Each new item copies it under the same serialized owner before publication. Retained items never substitute a new binding on reconnect. The host rejects a mismatched originating binding as Unavailable before preparing/enqueuing it. Replacement or key/epoch change therefore cannot silently resubmit old items under a new authority.

A successful result is installed exclusively before removing the matching claim. An identical existing result reconciles a retry; unequal bytes fence the claim. A full result budget backpressures forwarding while allowing Control progress. Workload result consumption acknowledges exact ID/digest before removing that result. A crash with result plus claim present retries the original bytes and reconciles the stored result. Expiry of an application wait does not silently discard the spool item. This is local retry custody on an ephemeral guest filesystem, not accepted-durable mailbox delivery.

The host key is `(actual VM instance, sender boot, tenant, authorization domain, granted mailbox, execution epoch, policy generation, GuestRequestId)`. Those scope fields come from the admitted launch and current host authority. A filename, guest-supplied ID, digest, connection generation or port is never authority. Derive stable canonical message/correlation IDs from this tuple with separate MVM domains and checked counters. Preserve the first prepared envelope, nonce and canonical sequence for retries. Never seal a new envelope for the same admitted request.

The immutable request identity includes every Submit field, including body and reply token. Its semantic digest is SHA-256 over `mvm.mailbox.local.request.v1\0` followed by the complete opcode-1 frame body, excluding the four-byte length prefix. Store the bounded original encoding plus this digest in the pending entry. Same ID and unequal bytes returns Conflict. A retry with identical bytes rechecks current authority before returning its original disposition. The digest is an index/comparison aid; it does not replace the exact comparison.

The producer adds a new item exclusively and returns Full when the existing count or byte bound cannot admit it. An active forwarding claim does not block new appends that fit the shared spool budget. The agent claims only the oldest item, atomically, under the same owner; it completes or explicitly abandons that claim before forwarding a later ID. Reconnect reads the retained claim first. A malformed item is quarantined within the same quota and surfaced as a typed local failure. No normal producer write overwrites a queued item or claim. Reliable mode must serialize count checking and publication, since the existing legacy count-then-create path alone is not a concurrent reservation.

Only a matching positive SubmitResult with request ID, digest and service generation permits removing the claimed item. Partial writes, EOF, lost verdict, Full, Backpressured and unauthorized/expired outcomes retain it. The workload may explicitly abandon a refused item through Cancel followed by Retire. Removal failure remains observable and retryable. The guest publishes the local result before unlinking and reports unlink failure rather than manufacturing success. A reconnect before removal resends the same bytes and ID. A terminal refused oldest item can block later dispatch until explicit abandonment; it cannot be silently deleted to make the queue look healthy.

After observing and storing a positive local result, the guest sends Retire on Control and waits for its matching result before forwarding the next claimed item. A missing Retire retains the host dedup entry and its charge. The host retains a constant-size retired-ID high-water mark and rejects an old absent ID as Retired. New IDs increase; gaps are allowed and cannot reset it. One active forwarding claim makes ordered retirement implementable while the producer continues to append many items. Retire releases only local producer retry state. Canonical destination deduplication and pending delivery/Call ownership survive until their own expiry and retention rules.

At helper crash/restart initial acceptance is ephemeral. A fresh host service generation invalidates retained local bindings and the guest receives Unavailable, never a fabricated Duplicate. Preserve affected spool items/results for explicit recovery. Relaunch uses the actual ledger epoch, reminted grant and fresh launch secret. Exactly-once effects or durable accepted state require a journal and key-retention/activation design beyond this slice.

## Host transaction, budgets and reauthorization

Extend the original helper's one `Shared` service state to retain prepared envelopes, bounded verified inbound values, Call entries, local dedup entries, reply tokens and replay/destination receipt state. Add a broker-owned aggregate budget passed into each service, with host, tenant, sender and mailbox sublimits. A service cannot mint independent host-sized budgets. Reserve before allocating request/body buffers, preparing crypto, admitting replay state or promising queue ownership. Use checked arithmetic for raw request, prepared envelope, decrypted value, in-flight wire copies, indexes and control records. Bound active connections, worker stacks, timers, lookups and retained records as well as payload bytes.

Start with host 64 MiB retained mailbox bytes, tenant 16 MiB, sender 2 MiB and per mailbox 512 KiB as conservative ceilings, subject to any smaller installed budget. Reserve 256 KiB of the host budget for control and at most two 4 KiB control-frame slots per admitted VM, accommodating a bounded canonical receipt and local header. The control allocation participates in the aggregate total and admission may refuse another VM. This is a proposed qualification envelope, not a measured capacity claim. Existing lower launch limits win. A configured sum is never a promise to allocate all maxima simultaneously.

Under a short synchronous state transaction, validate current scope/version, immutable ID, replay disposition and available credits. Prepare canonical bytes outside the state lock using a reserved provisional entry. Reenter to recheck the same policy/epoch/owner generation and publish the prepared entry plus queue reservation atomically. A losing duplicate preparation is discarded and its reservation released. No socket I/O, wait, guest dial or audit file write runs while this lock is held. A positive result is eligible for sending only after publication. QueueFull or failed crypto before publication releases provisional state and sends no positive result.

Use the canonical verified-open proof to retain the authenticated header with plaintext. Extract a narrowly scoped current-authority revalidation helper from existing canonical validation if needed. It must recheck recipient/mailbox, allowed kind and operation, content type, capability, expiry, revocation, both epochs, and the unchanged authenticated key-set generation. It cannot waive a replay check on a new envelope. Already accepted retry entries have their original replay decision; acknowledgments require fresh policy validation without decrypting/replaying them as a new delivery. Key changes fence the old generation. No arbitrary caller-supplied "always true" replay protector is an acceptable shortcut.

Canonical destination deduplication is bounded through message expiry plus the declared retention interval, as ADR-057 requires. Admission reserves that future retention cost. Exhaustion refuses new messages; it never evicts an unexpired accepted identity to make a retry appear new. Use one broker monotonic origin and a serialized dispatch sample for ordered state transitions, with trusted Unix time only for canonical expiry. Do not hold this dispatch lease across I/O.

## Return delivery and Call semantics

Host-to-guest Deliver accepts only an already canonically verified value authorized for that granted guest, including Receive authority. Preserve the actual verified header. Each bounded delivery gets a stable sequence and remains held until its matching DeliveryAck. A missing/full/partial acknowledgment retries the same immutable value. The guest inbox deduplicates that sequence within the bound generation. Unacknowledged entries apply backpressure. They do not consume the Control reserve.

For guest-to-host application consumption, add a typed claim/ack variant to the original local Unix host API. Claim retains the value and its authenticated identity. The client writes the required existing audit entry before AckRead releases it. Audit failure keeps the claim and refuses application delivery. Repeated claim/ack use stable IDs and idempotent audit identity. Preserve legacy `recv` separately; do not use its destructive take as the reliable implementation. The privileged Unix host API and guest vsock opcodes remain distinct decoders and authority checks.

The public producer operations are `cast`, `call`, `reply` and explicit `cancel`. Cast completes at local ephemeral admission and never creates an application Reply. Call first reserves a Call slot, then sends through the same admission path and awaits one verified Reply. Host-generated correlation is unique to the source principal/boot/execution epoch and binds the canonical Call message ID. A guest cannot reuse a correlation to target a later Call. Reply matches the expected authorized sender, destination mailbox/recipient, reply capability, original correlation and original Call causation. Destination and source execution epochs may differ and are checked in their respective scopes.

Cancellation and deadline expiry close only the local wait and retain the appropriate terminal record. They do not assert remote rollback. A later verified Reply is recorded Late and disposed under bounded retention, never delivered to a newer Call. The guest receives typed Deadline or Cancelled on Control. Receipt verification, object-v1 verified commit, inbox admission, host audit delivery, application Reply and application execution remain separate states.

SpiralCore uses existing object-v1 frames as application payloads inside this service. Split them only using the shared endpoint mapping's bounded framing contract. No new codec or mailbox envelope is introduced. Compress before canonical encryption at the authorized plaintext endpoint. Host relays retain canonical ciphertext transport semantics.

## Required tests and delivery boundary

Freeze legacy bytes and old signed-plan signatures. Exercise reliable mode refusal before side effects, exact wire vectors, malformed/oversized frames, every kind/operation combination, deterministic lost verdict and reconnect, concurrent slot writers, ID conflicts/retirement/wrap, queue and aggregate saturation, control progress during stalled data, authority changes during preparation/send/resume, replay retention exhaustion, helper restart generation changes, audit failure, reversed Replies, late Replies and idle/stalled shutdown. Verify original process ownership and reap in the actual native witness.

Native qualification begins with one guest and the original helper, then two guests under a small orchestrator. Record exact lengths/readbacks, setup and both-direction framing/ciphertext bytes, CPU, queue memory and verified total time. The existing [#42](https://github.com/R4-Laboratories/SpiralCore/issues/42), [#44](https://github.com/R4-Laboratories/SpiralCore/issues/44) and [#49](https://github.com/R4-Laboratories/SpiralCore/issues/49) platform, WAN and capacity gates remain required. This contract adds no certification or host-blind claim.
