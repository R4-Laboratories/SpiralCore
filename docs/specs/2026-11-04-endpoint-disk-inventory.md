# Durable inventory for disposable endpoint stores

Implementation contract under the resident-parent plan, #43/#49. This covers
only the explicitly disposable private codec/cache/staging directories of the
installed network endpoint. Canonical audit history, user files, mailbox durable
delivery records and the standalone durable object store are excluded from
deletion. No network frame, MVM envelope or object format changes.

## Original ownership and admission

Use the existing installation owner and original validated directory. Add the
inventory parser/I/O as one child module of `installed_owner`, reusing its
private descriptor, ACL/filesystem, file-identity and synchronization helpers.
Do not reconstruct the installation by path or duplicate its state parser.
The resident bridge pairs every inventory entry with an actual reservation from
the SAME managed pool before directory creation or child activation. Recorded
amounts are projections, never a constructor for independent credit.

Use a bounded, versioned checksummed inventory: at most16 entries and64KiB total.
Each entry binds installation/profile/generation, unique original partition
serial/session, stable tenant tag, opaque relative directory component, cache/staging ceilings,
creation/active/cleanup phase and captured directory identity when available.
Names are generated by the owner and cannot contain separators, dot components
or caller-supplied paths. Reject duplicate identities, overflow, noncanonical
records, unsupported versions and changes to retained descriptor identities.

Publish durable creation intent before creating the uniquely owned namespace.
Synchronize the new directory and parent, then atomically publish captured
identity/active inventory and synchronize its parent before exposing it to a
child. Preserve incomplete intent; error/Drop after possible creation cannot
refund disk credit or report an empty inventory. A definitely unused preparation
can be canceled through its actual internal phase. There is no caller boolean
or PID-based cleanup proof.

## Live cleanup and crash recovery

The resident composite retains the actual original `OwnedEndpoint` and its store
owner. Its successful shutdown must establish the same session/partition's
Drained state, zero trustworthy local reservations/quarantine, and positive exit
of that original child. Only then may its private cleanup path remove the
recorded disposable namespace. Failed cleanup retains the inventory entry and
actual disk reservation; native VM RAM and other service queues have distinct
owners and must not be refunded by a disk counter reset.

Durably publish CleanupIntent before the first unlink. Cleanup validates the original private namespace and retained descriptor, then
walks only that namespace under explicit depth/entry/work limits. Refuse links,
mount/device changes, foreign ownership, unsupported entries or identity
substitution. Use descriptor-relative operations; synchronize changed directory
parents before retiring the entry and synchronizing inventory publication.
Only the matching durable CleanupIntent can resolve a missing namespace as
already removed. Active plus missing/replaced data is not cleanup proof.

After a parent crash, the fresh installation owner must first obtain original
owner exclusion and kernel resource-holder exclusion. Only the recorded owned
disposable namespace is eligible for orphan recovery; a surviving child keeps
recovery Busy. Resolve creation/cleanup intents conservatively with bounded
descriptor-relative inspection. Ambiguous foreign identity remains quarantined.
No broad home/temp-directory cleanup is permitted.

Generic `begin`, `finish` and `reconcile` cannot publish Clean/start a new epoch
while inventory or incomplete disk intents/temp markers remain, even if the
main inventory file is absent. This guard applies even if
the prior process's in-memory managed ledger has vanished. The explicit recovery
path either proves cleanup and durably empties the inventory or refuses. It
cannot initialize a fresh zero disk quota over retained old stores. A missing
inventory preserves installations that never selected this endpoint profile
only when all disk metadata is absent. The generic owner guard may conservatively
refuse any disk metadata; the explicit inventory owner must durably remove a
verified empty inventory before generic retirement. It must not maintain a
second partial parser in the generic owner.
The inventory publisher and generic epoch-transition guard must serialize on
the same original transaction lock through publication/transition, so a writer
cannot create disk intent between the absence check and Clean. Define one lock
order; never hold the managed accounting ledger over filesystem I/O or call
back into its owner check while holding a lock in the inverse order.

## Required focused evidence

Start with missing-API RED. Prove atomic before-effects quota refusal, fixed
record/work limits, unused versus uncertain Drop, live original-child exclusion,
exact clean shutdown, and crashes around intent/create/identity/publish/remove/
retire. Successor admission must remain refused until actual holder exit and
verified durable cleanup. Include malformed records, stale/foreign partition,
link/replaced directory and failed directory synchronization. Source-only or
private bookkeeping fixtures are not native process/crash qualification.

Independent architecture review approves the contract with the cleanup-intent,
absent-main-file, tenant-scope and bounded-walk clarifications above. Implementation
and real qualification remain required.
Endpoint parent partitions remain Unsupported until the actual inventory and
held-budget handoff are connected. The existing helper/bootstrap tests do not
establish aggregate disk admission or native MVM integration.

## Revised implementation decisions (2026-11-04)

Generic epoch transitions additionally inspect the bounded private installation
namespace and refuse any generated endpoint-store prefix, including when its
inventory was lost. A creation-intent entry with a present directory has no
captured original inode and remains quarantined; recovery cannot adopt it by
name. An absent creation namespace can be retired after the holder barrier and
parent sync. This deliberately leaves the mkdir-to-identity-publication crash
window requiring explicit investigation, rather than deleting ambiguous data.

Directory traversal streams one validated name at a time. It does not collect
4096-name vectors at every recursive level. Depth is at most3 below the store
root and work is at most4096 entries per store. At most four held directory
streams plus bounded inventory/entry data are live during a walk. The declared
cleanup metadata allowance is512 KiB, shared by actual reservation identity
between the inventory and every prepared store. Dropping the inventory cannot
refund it while a store can still perform cleanup; close prevents new admission
but allows an existing owner to clean up. Numeric libc directory-buffer/setup
qualification and complete process memory remain separate release gates.
Fresh crash recovery currently has a bounded setup path, not a claimed new
managed-pool allocation; this setup envelope must be qualified before activation.

All modifying operations assume the installation directory is exclusively
managed by the original owner and its admitted holders. Prior substitutions and
links are explicitly refused. Arbitrary concurrent mutation by another process
with the same Unix UID is not made safe by path names or inode comparisons;
there is no same-UID hostile-process or power-loss qualification claim.

The focused process tests kill original Child handles at eleven publication
boundaries and require SIGKILL status. An ambiguous creation remains fenced;
other recorded states must recover before a fresh epoch. Two cfg(test)-only
hooks inject directory-sync errors; these model explicit I/O failure, not actual
power loss. There is no release environment-variable fault or cleanup bypass.

## Live original-child retirement

Add a private low-level owner operation for an already authorized original
endpoint retirement. It receives the actual mutable DiskStore, never a path,
quota projection or caller success flag. The higher resident wrapper must first
borrow the sealed original EndpointRetirement, compare its full projection/store
and exact retained guard identity, and retain that receipt through cleanup.
The I/O primitive does not manufacture the endpoint-exit proof itself.

Unlike whole-installation crash recovery, live cleanup does not require all VM
holders to exit: a different VM/service may still be live. It validates the same
owner/epoch and captured namespace identity, publishes CleanupIntent durably,
walks only that namespace under the existing limits, removes/synchronizes it,
and retires its inventory entry. The actual store,512KiB shared workspace and
disk reservation remain held on any error. Close admission permits cleanup.

Private in-memory progress records only positive original I/O: namespace removal
plus parent synchronization, then completed inventory publication. It permits
retry after a partial cleanup or final publication failure without resetting
credit. A missing Active namespace still refuses; a missing inventory entry is
accepted only behind the same store's previously observed durable removal, not
from serialized metadata or name absence. An incomplete temp publisher remains
quarantined for explicit recovery. Repeated completion is idempotent.

Focused tests exercise real stored bytes, a concurrently held original VM lease,
resumption after post-remove sync and final-publish failures, and refusal to
adopt missing/replaced Active namespaces. These are low-level filesystem tests,
not native MVM retirement or a substitute for the sealed higher-layer gate.
