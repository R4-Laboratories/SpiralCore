# Publication and engineering-facing project guide

User-authorized supplement to the active Ari delivery plan. Implementation stays
active; documentation must describe its executed state rather than imply release.

1. Publish reviewed source/evidence milestones to main and preserve current work
   as explicitly labeled development checkpoints on codex branches. Coordinate
   source snapshots; exclude local runtime/sessions, tooling state, targets,
   credentials and raw payload/VM stores. Pending MVM dependency pins and failed
   gates stay explicit. Do not merge an unqualified checkpoint as a release.
2. Replace the long chronological README with a network/socket engineering guide:
   protocol and endpoint roles, original-byte verification, codec/cache behavior,
   actual carrier/OSI boundaries, canonical mailbox/FlowMux/access paths, exact
   current qualification and reproducible result/report links. Keep a separate
   concise current-status document and GitHub roadmap authority.
3. Replace the four cartoon-style overview rasters with coordinated professional
   technical pictures: object reconstruction, NIC/TUN path, canonical MVM
   isolation and OSI placement. Retain pictures as pictures; add precise workflow
   sequence maps where needed. Illustrations are conceptual, not runtime evidence
   or specialized hardware requirements. Save prompts/tool/provenance and inspect
   labels/placement before publishing. Preserve old art in Git history.
4. Independently review claims, links, image captions and source/checkpoint scope;
   validate scoped source/tests where applicable, merge the documentation PR and
   update tracker checkpoints. Continue actual installed-service integration.
