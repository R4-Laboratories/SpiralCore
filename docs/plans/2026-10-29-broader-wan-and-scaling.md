## Design and comparison policy

Preserve exact bytes and original length, authenticated scope, final whole-object
SHA-256 verification, bounded resources and durable publication acknowledgment.
Keep historical evidence and default behavior intact. New experiment configuration
must be explicit and bound to the canonical plan and receipts.

The immediate delivery combines broader 16 MiB-class workloads with fairer controls:

1. An immutable receiver policy can disable optional raw/zstd DAG preparation.
   Mandatory DAG ingestion/validation is unchanged. All new comparison arms use
   the same byte-publication readiness policy; policy is recorded in the plan.
2. A versioned, bounded zstd prefix-dictionary delta is the first conventional
   delta control. It uses the already pinned zstd library, one verified authorized
   base and the same transport/publication contract. This is a configured zstd
   prefix engine, not an implementation or qualification of rsync/VCDIFF and not
   a claim of exact `zstd --patch-from` CLI parameter equivalence.
3. Compare raw full copy, ordinary zstd, zstd prefix delta and SpiralCore sparse
   COPY/LITERAL, with all encoder/base setup and teardown inside the timed work.
   Seed each arm separately; permit raw fallback only before Begin, record it,
   and never interpret an unexpected target cache hit as a successful update.
4. Use fresh quota-safe shards. Every recorded successful output must be reopened
   and independently regenerated byte-for-byte. Both body-byte directions, frame
   counts, CPU, wall time, source/executable/fixture identities, seed cost and all
   negative cases are retained. Pure network time and energy remain unmeasured.

Alternatives considered: external xdelta/rsync through a separate process/transport
adds an unmatched trust/readiness boundary; a new in-house VCDIFF matcher would not
be an independent established-engine baseline. Retain those as future controls.
Zstd's existing implementation minimizes dependency changes and enables a matched
authenticated path. Its dictionary preparation cost is counted, not precomputed
outside the operation.

  default preserved; adjust optional admission charge and optional fold together.
- `src/protocol.rs`, `src/client.rs`, new prefix codec module and focused tests:
  versioned prefix mode with authenticated base identity, encoded/output/window
  bounds, exact single-frame decode and raw fallback; no subprocess decoder.

### 3. Cache-cost mechanism attribution

### 4. Larger client/resource qualification

### 5. Sustained operation and recovery

- Extend sender/receiver integration tests and benchmark scenarios for version

- Use genuine network shaping for latency/bandwidth/loss/jitter controls; retain
  direct-versus-relay scope and both directions. Measure energy separately before
  any joule-saving claim. Risk high; depends on stable transfer/resource contract.

## Final MVM integration boundary

After standalone optimization/qualification, implement a separate adapter between
the transfer engine and MVM's approved vsock mailbox service. It must support a
small MVM network and its orchestrator: authenticated node and recipient identities,
mailbox addressing, tenant/capability isolation, lifecycle/discovery, backpressure,
retries, resume and epoch/revocation behavior. Preserve at-least-once semantics and
separate object commit, mailbox admission, delivery and application processing.
The exact vsock binding comes from MVM's canonical mailbox contract; FlowMux port
5253 must not be invented as a mailbox interface. Cooperative policy-controlled
network streams are a later integration layer. WASM is deferred.

## Acceptance and evidence

All successful results must be exact after reopen; failures must not produce a
verified commit. Compare against the best applicable measured baseline, including
seeding, and report fallback or regressions per workload. Warm byte/time targets
remain 90% byte reduction and 2x completion advantage where the workload supports
reuse; these are hypotheses, not promises across all edits. Cold targets remain
at most 5% extra bytes and 10% extra p95 time relative to the fair secured raw path.
Separate source changes, qualification, scientific measurement and interpretation.
Each phase produces reviewable commits, raw receipts and an updated claim ledger.

## Registered broad16 workload schedule

The v4 suite names are `broad16-` followed by one of `localized_32`,
`scattered_32x32`, `prefix_4096`, `middle_4096`, `delete_4096`, `append_4096`,
`truncate_4096`, `replace_1m`, `structured_localized_32`,
`compressed_localized_32`, `cold_random`, `cold_structured`.
Each case has 30 global trials split into five fresh-cache shards of six trials,
four arms (raw_full, zstd_full, zstd_prefix, sparse), and identical paired inputs.
Warm arms each have a separate raw seed immediately before the update; cold arms
have no seed. Thus the complete matrix has 2,640 operations across 60 shards.
This is a broad qualification workload, not a promise that every arm/case wins.

Each suite uses all 24 arm permutations before repeating; the 30-trial design is
not fully balanced for carryover. A single campaign ID derives seeds and order.
Insertion/append bases are 16 MiB minus 4096 bytes and targets exactly 16 MiB.
Deletion/truncation targets are 4096 bytes shorter than their 16 MiB bases.
The compressed fixture is a valid zstd frame of 16 MiB minus 4096 pseudorandom
bytes, followed by a 32-byte opaque midpoint mutation. Its target is not claimed
to remain a valid compressed stream. Actual lengths and identities are recorded.

All four arms use `cold_graph_warming=false`, bound by receiver plan, source,
executable and startup-policy evidence. Warm sparse and prefix retain exactly
their owned base bytes from the seed and destroy that retained state inside the
update timer. Prefix setup/encoding and raw fallback selection are timed. Cold
sparse uses raw; cold prefix uses ordinary zstd. This deliberately exposes the
limitations of fixed codec selection; it is not an adaptive-best-codec claim.

Per-shard maximum payload is 768 MiB plus bounded publication headers, below the
unchanged 1 GiB cache quota. Fresh caches, same source/settings, exact reopened
verification and all observations are mandatory. No performance trial is replaced
because of a poor result. Setup failure before the first measured operation is
recorded separately. A partially executed shard remains incomplete evidence.

Preserve raw receipts, packet files, exact verification and per-publication hashes.
After independent reopen verification and hashing, completed new synthetic cache
directories may be removed to keep this campaign within local disk space. Record
that cleanup explicitly; do not remove any prior campaign cache or evidence.
Raw PCAPs remain local and hash-bound to compact committed records. Hosted artifact
retention is one day. No paid host is provisioned.
