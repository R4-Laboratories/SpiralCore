# SC-OPT-003: opt-in SHA-256 backend experiment

Status at registration: NOT_RUN. Baseline production source is the reverted SC-OPT-002
state at `cb376b80dd5f54decdac124611c3ff24417e7fd1`, identical to the measured SC-OPT-001
implementation. SC-OPT-002's complete negative result and rollback are retained separately.

## Hypothesis and bounded change

Enable the existing sha2 0.10.9 assembly feature through a default-off
`hardware-sha256 = ["sha2/asm"]` Cargo feature in spiralcore-transfer. On this native
Apple ARM host this selects the library's SHA2 instruction backend, with the library's
dispatch behavior. Keep all production Rust, identities, wire format, quota and commit
semantics unchanged. Add only the pinned sha2-asm 0.6.4 dependency and necessary lock edges;
do not update existing package versions or checksums. This is a build experiment, not a
new hash algorithm or a cryptographic-module validation.

Both software and hardware variants must be built from the same committed source and
expanded lockfile. Only the named Cargo feature may differ. Capture effective feature
trees, source and helper hashes, compiler/target/toolchain/environment, build commands and
executable hashes. Use native aarch64-apple-darwin release builds with no target-cpu=native
or global target-feature override. Keep the portable default unchanged. Other target and
unsupported-hardware behavior is unqualified; the upstream assembly dependency rejects
Windows builds. Record this limitation in the architecture decision and user documentation.

## Correctness and configuration qualification

Run the complete transfer test targets, doctest, fmt and clippy under both configurations.
Run imported-store tests under the unified dependency feature where feasible. Existing fixed
independent protocol vectors, canonical DAG oracle fixtures, malformed-input, authentication,
quota and durable-publication tests must pass. Confirm no production Rust changes and no
existing locked dependency drift. Run independent standard SHA-256 padding and multiblock
vectors as helper qualification if not already covered; qualify any new helper before timing.
The diagnostic probe must preserve the prior source and fixture behavior, validate exact
Ready/Accepted/Published replies, and compare target and base bytes after closing/reopening.
No failed or skipped observation may be silently removed.

## Registered measurement

Copy the previously reviewed Rust receiver probe into a new experiment directory; preserve
SC-OPT-002 sources, binaries and receipts unchanged. Retain the same 16 cells: background
objects N=0/64/256/768, raw/sparse update, max_nodes=262144/1. Both graph-cache retention
knobs remain zero. The one-node policy also affects admission and is not a pure warming toggle.
Normal raw Finish constructs a graph while sparse Finish does not; compare each arm against
its identical off/on counterpart. Fixture: xorshift64-low-byte-per-step-v1, seed42, 1MiB,
32 bytes XOR165 at offset524288. It is not the earlier WAN fixture generator.

Use eight paired blocks, software-first in even blocks and hardware-first in odd blocks,
with the previously fixed within-process population/arm rotation. Every observation starts
from a private synchronized clone of an identical closed template, with the target absent.
Preserve template before/after hashes. Do not run builds, tests or another benchmark during
timing. Record host snapshots but do not retrospectively normalize for them.

Primary metric is `local_operation_total.cpu_ns`: recipe/frame preparation through validated
publication and request-buffer destruction in the same process as the endpoint. Handler CPU
is a subset, not an additive cost. Report stage CPU/wall, whole-operation wall, separate
cloning/open/reopen-verification costs, modeled bidirectional application-frame bytes, exact
identities/readiness, all eight paired values, marginal midpoint medians, nearest-rank p95,
and geometric mean of matched software/hardware ratios. With eight samples p95 is the maximum,
not a stable tail estimate. This is 256 observations in 16 processes, not 256 independent
samples for any one effect.

All three CPU criteria must pass for this experiment's performance hypothesis to pass:

| Cell | Minimum paired software/hardware geometric mean | Hardware faster pairs |
|---|---:|---:|
| N0 raw, max_nodes262144 | 1.10 | at least 6/8 |
| N0 sparse, max_nodes262144 | 1.50 | at least 6/8 |
| N768 sparse, max_nodes262144 | 1.20 | at least 6/8 |

Report every other cell, regression and control result. Do not substitute a favorable cell,
drop an outlier, increase trials after seeing results, or multiply this ratio by a prior WAN
ratio. Any setup failure is retained outside the performance sample with its disposition.
Preserve the default-off feature even after a local pass until deployment targets are qualified.

## Recording and review

Before measurement, commit the plan, schedule, candidate feature/lock and helper/build provenance.
Afterward retain raw JSONL, commands, execution order, source/executable manifests, configuration
and independent arithmetic/identity review under `docs/network/evidence/2026-10-29-hardware-sha/`.
Update the optimization ledger with the observed outcome, including a miss if applicable.
Keep generated diagnostic console logs separate from scientific receipts and remove owned empty
or redundant diagnostic logs after recording checks. Preserve raw evidence byte-for-byte.

This experiment does not measure a network, WAN latency, total-path traffic, energy or power.
It cannot establish FIPS validation, production readiness, unsupported-CPU fallback behavior,
or a remote host speedup. A local pass can justify a separately recorded deployment experiment.
