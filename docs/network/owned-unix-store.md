# Descriptor-rooted Unix object storage

The opt-in SmallV1 receiver can use directories that its resource owner has already opened. It provides a descriptor-backed alternative to the synthesized procfs path associated with the installed macOS FlowMux preparation failure. The frozen installed MVM host adapter consumes an earlier reviewed pin; adopting the explicit workspace contract below into Ari's current owner remains a separate gate. The existing Path constructors and Windows backend retain their behavior. Object identity, v1 frames, codecs and per-operation authorization use the same implementation.

## Custody and operation

1. The embedding reserves its aggregate storage, workspace, descriptor and traversal capacity before creation. It retains the original parent, generated child name and opened child on that reservation.
2. `OwnedStorePolicy::workspace_requirements(&limits, lanes)` derives the requested heap layouts and separately required existing worker stack. `OwnedStorePolicy::small_v1(&limits, funded_entry_visits, lanes, funding)` requires an `OwnedWorkspaceFunding { heap_bytes, existing_stack_bytes }` declaration from the original reservation. Short funding refuses before capture or filesystem effects. The policy binds the exact authenticated `Context::namespace()` IDs and receiver limits; its closed lane input permits one or two distinct IDs. Membership and numeric funding grant no authorization.
3. `OwnedStoreLease::capture` checks the original descriptors and named child without creating or removing filesystem contents, then fallibly allocates its funded buffers, bounded index and scan records. The embedding attaches a lease clone to its reservation before endpoint initialization.
4. `ObjectEndpoint::open_at_with_resource_profile` claims that lease once. It installs the actual opened owner file in retained custody before further validation, holds the kernel writer lock, initializes or validates the profile, and performs bounded recovery.
5. Reads, quota scans, staging, publication and ordered eviction use checked names relative to those descriptors. Begin and Commit each make a fresh quota decision. Before a positive cached receipt, the receiver verifies the bytes and successfully syncs the file, namespace and original root. A failed post-rename sync can leave a named file, but cannot justify a positive receipt until that barrier succeeds.
6. After admission ends and every endpoint and reader is drained, the original owner calls `retire_contents` with exclusive lease custody. It preflights the complete store before deleting data and removes the owner name last. The embedding retains the original locked file through its own parent-relative removal, parent sync and confirmed absence. Failure retains the original reservation and attained resources in quarantine.

The default policy processes at most 101 entries across both lanes and requires funding for 102 observations, including overflow detection. Markers, directories, publications, stages and unknown names share that walk budget. Recovery and retirement preflight also enforce the publication and staging sublimits; Begin and Commit independently enforce publication quota. Cleanup permits at most 103 bounded walks, with no automatic retry after uncertainty.

## Platform and resource boundary

Linux requires working descriptor-based mount-ID lookup. macOS requires the checked local, non-union APFS mount shape. The embedding must own the private mount tree and exclude independent same-UID writers and mount substitution. Relative stat and unlink are not an atomic compare-and-delete against a hostile concurrent host process.

One controller shares its parent descriptor. Each prepared store retains two descriptors, for its child and original owner file; lease clones duplicate neither. Serialized nested traversal is tested with at most four transient descriptors. The embedding must fund the corresponding maximum concurrent stores, iterator allocations, bounded names, metadata, verification buffers and stacks before activation. A descriptor count or observed RSS alone does not establish that memory budget.

Each store retains two 16 KiB directory buffers from capture through final store destruction, including quarantine and successful `retire_contents`. `OwnedStorePolicy::directory_buffer_bytes()` still quotes only their 32,768-byte payload. The composed `OwnedWorkspaceRequirements` also includes the Store/Arc layout allowance, the full bounded ordered index and simultaneously live scan vector, and Darwin's three native mutex backing payloads. Every vector must have exactly the requested capacity before claim/recovery; excess capacity is refused without an infallible shrink. Mutex backing state is initialized before publication so it cannot allocate lazily during later metadata operations.

The index and scan are preallocated at capture for at most 64 publications. Their one permitted transfer into the ordered endpoint retains the original lease; the scan and index storage drop before that guard can release original custody. A failed scan or constructor preserves this ordering. Protected IDs, pending quota entries and eviction candidates/victims use bounded stack arrays. Names, C-string arguments and profile verification use fixed stack storage, including supported long Darwin components. The existing total age/ID victim order, complete object verification and exact namespace/hex transcripts remain compatibility boundaries.

The layout model is admitted only for Rust 1.97.1 commit `8bab26f4f68e0e26f0bb7960be334d5b520ea452` on Linux GNU x64/ARM64 and macOS x64/ARM64. Other compilers/targets return `Unsupported` from the owned policy; existing Path/Windows APIs have no added compiler gate. The model derives actual type layouts: pinned std's Arc header fits the checked Store-alignment plus 64-byte allowance; Linux uses inline futex mutexes, while Darwin uses boxed `pthread_mutex_t`. This is requested allocation payload, not a universal malloc, fragmentation or RSS bound. Original-owner enforced memory remains an explicit precondition for physical allocator effects, and kernel/descriptor terms keep their existing payer.

The separate 2 MiB stack requirement refers to the existing funded session/reader worker, never an additional codec debit. Native component controls query the actual worker stack and exercise the supported call chain; they do not establish an original runtime permit. Byte-returning payloads, attempt/history/decoder state and caller-owned authority remain charged by their existing profile/owner. The installed adapter's existing 1 MiB filesystem floor must remain reserved through final destruction; a derived requirement above that floor must refuse rather than enlarge a host budget. Its actual enforced-owner receipt and current-MVM adoption remain acceptance gates, including continued production refusal on a platform without qualified enforcement.

A complete walk borrows the original store's buffer pair with `try_lock` before opening any iterator descriptor. Contention or reentry refuses with `Limit`; poisoned work state refuses with `Storage`. There is no waiting queue, growing buffer or alternate iterator fallback. Independent stores retain independent pairs. Linux uses rustix's caller-buffer `RawDir`; macOS uses the narrow `spiralcore-directory-macos` boundary to `getattrlistbulk` on a freshly opened and verified descriptor-relative `.`. Darwin records are bounds checked, attribute/error fields validated and names borrowed only until refill. API/filesystem failures refuse. Names remain discovery only: fresh private owner/mode/type/link/mount and held-versus-named checks still decide every subsequent operation. Core Rust retains `forbid(unsafe_code)`; only the macOS helper contains its documented FFI boundary.

The implementation is an opt-in component, not evidence of installed MVM or WAN acceptance. Native component tests cover original-parent renaming and substitution, exact trailing-NUL reconstruction, warm reuse, live authority, independent Commit quota, subprocess interruption, failed sync and original-lock retention. The original macOS relay custody fixtures now pass. Complete installed-parent qualification, native guest lifecycle, supported capacity and final cross-host acceptance remain separate gates.
