# Qualification corrections and limitations

The RED run retained the original verifier. Two workers each held one original store, 64 private maximum-artifact publication-format records, 32 object stages, one profile stage and both enrolled namespaces (101 entries). Records were manually preloaded and read back exactly. This is filesystem evidence, not application, network or MVM admission.

The allocation window counts every newly requested Rust payload byte during retirement, coordination, assertions and fixture destruction. It does not subtract frees of pre-window allocations. It excludes allocator metadata/fragmentation, direct libc allocation, native stacks and RSS. Retained directory buffers predate the window; the 1 MiB/store quote is not an original MVM permit. Start barriers allow concurrency but do not prove simultaneous verification peaks.

The RED launch requested 6 GiB / zero swap / 200% CPU, jobs 2, Rust 1.97.1 and the shared target. No active configured-limit receipt was captured for that fast run; garbage-collected unit defaults are not evidence of actual caps. The wrapper exited 0 only after observing cargo exit 101 and the exact allocation-refusal text. The clean source archive and raw test log remain. The independent RED executable hash was not captured before rebuilding.

The initial macOS archive carried provenance headers that GNU tar warned about. COPYFILE_DISABLE=1 and --no-xattrs produced a clean archive with the same Rust source before execution. The redundant initial archive was later removed after verification; the clean RED archive is retained. This was an export correction, not a product or test relaxation.

Initial GREEN passed the new filesystem witness and all seven metadata tests. Strict all-target Clippy then failed because the minimal export omitted existing compile-time schema fixtures. Five unchanged Git-tracked inputs were supplied; strict all-target Clippy subsequently passed. The original compiler failure log remains.

The final source strengthened repeated Interrupted coverage and added distinct allocation, worker-retirement and whole-window timing labels. Its 207-input export has SHA-256 ef922b02bfc1976836280a39d9ebd91d26e7ec6665bfb0190b97d8b0588d4492. The exact selected executable passed the direct witness and retained its hash. Actual active 6 GiB / zero-swap / 200% CPU receipts are recorded.

That first final all-target execution stopped at three bounded_selection_workflow tests because a runtime workflow file was missing from the export. The raw exit-101 log and 207-input manifest remain. Eight unchanged workflow files explicitly read by existing tests were supplied. The corrected complete set has 215 inputs and ran under a new unit/log name, preserving the earlier failure. No source, assertion, timeout, lint or security check changed for the correction.

The complete run passes 530 transfer tests with four pre-existing ignored, one doctest, strict all-target Clippy and 87 FlowMux tests. All 215 input hashes match the committed checkout before and after execution; the direct witness executable remains unchanged. The 207-input archive plus the eight-workflow supplement reproduce the complete set.

RED largest/cumulative requests are 65,536 / 16,889,866 bytes. Final direct requests are 250 / 112,650 bytes with 8,394,880 exact record bytes. These are instrumented requested-payload observations. They do not prove old live-budget overcommit, a hard workspace/RSS bound, or timing improvement. Final setup, per-worker retirement and whole-window clocks are separate and include the scopes printed by the witness.
