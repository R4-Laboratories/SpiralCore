# Waiting for an empty object mailbox on Firecracker

The fixed five-millisecond cadence remains the default. In two matched comparisons, a caller and receiver that waited progressively longer after an authenticated Empty response used fewer warm guest-stream bytes but took longer to finish every measured phase. The cold byte result reversed with run order. The experimental code changes only the guest applications' wait following Empty. It resets the delay for each logical receive, polls immediately on entry, and caps subsequent waits at the smaller of the remaining original deadline and 5, 10, 20, 40 or 80 milliseconds. In the first comparison adaptive used 62,499 fewer guest bytes cold and 16,027 fewer warm. In the reversed comparison adaptive used 21,472 more cold bytes and 7,537 fewer warm bytes. Its extra elapsed time was 2.404 s cold and 0.553 s warm in the first comparison, and 2.806 s cold and 0.595 s warm in the reversed comparison. Each cold operation sent 4,096 Raw data bytes, with 4,658 object-frame bytes in both directions. Each warm operation sent 190 object-frame bytes and zero data bytes. B read back the exact original 4,096 bytes eight times. Each pair retained the same authorized receiver worker and boot across its two phases. [Per-direction increments, original-observer hashes and nanosecond measurements](empty-pacing.json)

**Meter scope.** Each port 5257 total counts completed bytes between the host helper and its own guest after native multiplexing. The sealed totals count each independent helper direction once, with the receiving meter matching its opposite sending meter. On this fixture, completed rows with 400–599 bytes read by the host and 3,000–3,999 bytes written have the size of an empty selected read. Such reads send the original Receive challenge and credentials, verify fresh proof of possession, and return Empty. The original counter format stores only sizes and errors. “Empty-shaped” is a size classification, while the table's total bytes and turns are direct counter differences. Role bootstrap occupies a separate interval with A/B turn counts of 1/1, 2/1, 1/1 and 1/1. B's fresh authorization of an existing Call and its lease ACK have separate message shapes. No challenge, signature, policy or absolute deadline changed. **Lifecycle.** An earlier fixed-cadence attempt refused the original B local volume lifecycle lock before either helper was returned. The paired A admission cancelled. Both VMMs remained unstarted, and the original driver recorded one audited entry and zero sessions. All four subsequent pairs completed their data phases with zero measured I/O errors and all six original counters closed. The first three pairs' helpers exited zero unassisted. The fourth pair's original A helper exited 1 unassisted, B exited zero, and the driver returned 1. No Firecracker process, mailbox helper or active VM scope remained after the reverse sequence. Each completed transfer pair had a verified audit chain with 17 entries and two sealed sessions. A lifetime 5257 write error occurred outside the measured phases in each of the first three pairs.

**Execution.** Each trial used a fresh private installation, two actual Linux x86-64 Firecracker guests without a NIC, the same host debug binaries and canonical guest agent, and release-built workload binaries. The new images were sealed from the experimental guest source, with executable readback from ext4 before launch. All transfers used the original signed operations, journal acceptance and guest ACK. The whole driver process accounted for 7.604, 7.629, 7.764 and 7.786 CPU seconds across the four runs. External lifecycle wall time was 15.41, 18.34, 15.47 and 12.05 seconds, respectively. The two matched comparisons cover one object and one host. WAN, fleet and tail-latency measurements remain open. [Installed object tracker](https://github.com/R4-Laboratories/SpiralCore/issues/202)
