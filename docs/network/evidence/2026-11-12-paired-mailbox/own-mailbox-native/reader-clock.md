# Firecracker guest reader validity window

The original workload's Receive in trial 5 began **677 ms before its signed reader enrollment became valid** and ended **606 ms before validity**. The guest wrote 54 bytes and read a 77-byte refusal on its local application reader socket over 71.136 ms. An offline replay used that boot's actual signed enrollment, receive capability, ACK public key and boot record. The canonical verifier returned `NotYetValid` at both guest clock samples. It verified the signatures and scope at the exact signed issue time. The host retained one journal record, with the anchor at cursor 1. All rows used a fresh private home and tenant state, one vCPU, 256 MiB, the original production grant and the 313-byte application frame. The SDK stopped or rolled back each original guest. Host command times include setup and cleanup. Guest CPU, verified end-to-end completion, send-only time and WAN bytes remain unmeasured.

**Packet observations.** In trial 4 the original Firecracker debug log showed DATA header lengths totaling 435 bytes guest-to-host and 4,513 bytes host-to-guest on port 5257. Trial 5 showed 435 and 4,558 bytes respectively. Each guest sent a 381-byte outbox exchange and a 54-byte Receive request. Each host sent a response over 3 KiB to the Receive request. No subsequent possession payload appeared. These totals are lengths from the observed virtio-vsock DATA headers. They exclude control frames, physical network overhead and the separate guest-local reader socket. Trial 4 reached the configured worker recycling boundary. Its guest console reported recycling and produced no replacement announcement or host application result before timeout. The exact reason that terminal response was lost remains unresolved.

**Installed meter attempts.** Trials 6 and 6 repeat each retained the original helper meter file descriptor before teardown. The file contained only its header. Neither trial produced a closed measurement or an application Call. Each guest console reported a panic in a standard child-process wait on the entrypoint-validation thread, followed by guest init exit. The original audit chains verified with ten entries each. The evidence does not establish that enabling the meter caused the guest panic. [Meter source](https://github.com/Casey-allard/mvm/commit/bd43ebb76b8239978151aed0a6950190141811ee)

**Recovery criterion.** A guest may defer an authenticated credential until its own clock reaches the original signed window and verify it again at use. The current instant, signature, enrolled identity, epoch, scope, deadline and original expiry must all remain authoritative. Acceptance requires the guest to receive and exactly reconstruct the original, explicitly ACK, and advance the journal.
