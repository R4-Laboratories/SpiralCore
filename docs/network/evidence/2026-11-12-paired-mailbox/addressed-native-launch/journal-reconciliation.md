# Verified admission and the trusted-host journal

Ari’s journal draft already contains the verified-envelope, Reply authorization and borrowed admission APIs requested in the earlier contribution. Reconciling the two pinned drafts on the contribution fork produced **the same source tree as Ari’s draft**, including its compatibility alias and original journal tests. The two-parent commit records their relationship. [Fork reconciliation](https://github.com/Casey-allard/mvm/commit/2a8917f27f46e22d0b25b725be7d5dc935825f49) · [Journal draft #5377](https://github.com/tinylabscom/mvm/pull/5377) · [Admission API draft #5328](https://github.com/tinylabscom/mvm/pull/5328)

| Boundary | Behavior at the combined source |
|---|---|
| Open the signed message | `open_verified_envelope` authenticates ciphertext, header, identities, signature, capability, current epochs, time and replay. Both the journal’s compatibility entry point and the owned admission API delegate to this verifier. |
| Hand the result to a service | `VerifiedMailboxAdmission` owns the original ciphertext and verified plaintext. Its borrowed journal view exposes the immutable envelope, authenticated header, replay identity, commitment and historical verification scope. The journal’s current implementation calls the verifier through its compatibility entry point and stages replay locally. |
| Authorize a Reply | The outbound path requires the Reply operation, capability, and matching signed route for a Reply. The generic Send grant cannot replace it. |
| Commit at the destination | Trusted-host local acceptance requires current destination authority, the local journal, retained history key and same-host anchor. A newly committed V2 acceptance receipt follows the append and anchor update. A retry can reproduce the original signed acceptance under current authorization. The separate V1 durable tier requires an independent checkpoint and key custody. |

The two receipt tiers have distinct signing domains. Neither an authenticated header nor an authorized outbound frame is a destination receipt. Deployment still needs B’s enrolled destination authority and a transport that returns B’s verified receipt to A. This component qualification supplies no installed key provider, independent anchor deployment, or A→B guest transfer. ## Epoch regression

A sealed header at execution epoch **7** was presented to a verifier at epoch **8**, with an otherwise valid capability signed for **7 through 9 inclusive**. The capability admits both epochs, but the message still carries the previous epoch. The plaintext open and verified-header open each returned `MailboxError::StaleExecutionEpoch`. The owned admission regression also checked that refusal did not record a replay identity. The original `stale_or_foreign_epochs_are_fenced_on_both_sides` test remained byte-identical in both parents and passed. It separately exercises an owner behind the header, a matching epoch above the grant ceiling, and stale policy epochs. [Exact cases and fixtures](https://github.com/tinylabscom/mvm/blob/543efc7f94aa756c09785b38bdd024b6ba8199c7/crates/mvm-core/tests/mailbox_crypto.rs)

Linux passed 113 checks: 57 mailbox library tests, 27 crypto integration tests, eight reader and reader-wire tests, 14 delivery/receipt/retention contract tests and seven compile-fail API tests. The run used the clean journal checkout with the same complete Git tree as the reconciliation commit.
