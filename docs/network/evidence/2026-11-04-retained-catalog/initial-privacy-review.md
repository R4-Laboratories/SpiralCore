## Implemented privacy properties

- Original tenant/session/parent identity, original inventory identity, current reservation and actual pinned directory/files are checked. The two callbacks use the existing RegistrationBinding pin rather than accepting a caller-selected replacement path as authority. Completion requires the original opaque endpoint retirement receipt and original guard/projection; a caller-created status is insufficient.
- The catalog binds actual original encrypted-record and wrapped-key file identities. It does not decrypt, rekey, replace or delete them. Fixed filenames, no-follow opens, current owner/private permissions, single-link checks and identity comparison restrict substitution. Files are synced before publication stages. Faults close admission and retain custody/debt.
- R=8 MiB and K=32 KiB are reservations in the same aggregate managed budget. The fixed 16-row table and bounded canonical catalog limit metadata growth. These are source limits, not measured RSS or capacity evidence.
- Endpoint retirement seals retained records before disposable cleanup. Supervisor drain and `destroy_on_exit` do not authorize audit-data deletion. Nonempty retained custody prevents ordinary empty-owner reconciliation; Drop conservatively preserves original pins/credits until process exit instead of refunding them or silently erasing data.
- Reviewed error handling uses static error classes. No new diagnostic path was found that prints plaintext records, key bytes, arbitrary catalog contents or raw paths. No credentials or raw telemetry were dumped during this review.

## Required public wording and boundaries

The separate catalog is **plaintext sensitive metadata**: absolute state paths, opaque tenant/session/parent identifiers, filesystem identities, phases and ciphertext digests. Its checksum detects canonical corruption; it is not encryption, authentication or fresh authorization. Private local access is required. Do not call this an encrypted catalog or claim that tenant isolation makes it safe to disclose.

The owner preserves opaque files supplied by the canonical producer; it does not prove those files contain valid encrypted telemetry, integrate the production KEK lifecycle, certify the cipher/provider, or establish host-blind confidentiality. The reviewed API requires the canonical strict-key producer path. Source-level possession of records and wrapped-key FDs is separate from actual producer and native lifecycle evidence.

Use distinct acknowledgment language: file protection/binding, endpoint retirement, retained sealing, disposable cleanup, VM teardown and application completion are different events. A successful sealed catalog row does not authorize deletion or mean an application-level acknowledgment.

There is no implemented retention-expiry/deletion authority in this change. No retention policy should be inferred from VM `destroy_on_exit`, endpoint `Drained`, or a resource counter. Closed-debt adoption, explicit authorized expiry/deletion, failed-transaction retry/recovery, production profile construction and sustained operation remain open. Preserving data indefinitely can itself be a privacy obligation gap; document it as unfinished operational policy rather than representing automatic deletion as present.

For the stated unclassified/CUI target, this source is a preservation component on a path toward qualification. It establishes neither FIPS 140-3 module validation nor CUI/control compliance, government approval, production readiness or a supported native/platform/WAN capacity envelope. No concrete validated cryptographic profile is established in this packet. These claims require separate module/version/environment/mode and system evidence.

## Newly reported durability blocker (not a privacy disclosure)

Root reported a separate independent code-review finding: if an existing retained catalog disappears, a subsequent new B append can create a new catalog that forgets original A. This reviewer has not executed or independently reproduced the fault. Treat durable accounting/recovery as **HOLD**, including crash/restart preservation claims, until the original-owner beacon/expected-set design is implemented and a genuine fault regression is recorded. The scope/FD isolation observations above do not establish completeness of the durable inventory. This is functional durability/custody incompleteness, not evidence of plaintext disclosure or permission to delete. Root accepted the conditional macOS observation and intends a shared directory predicate fix; that subsequent source is outside this frozen review.

## Disposition

Production/retention lifecycle, native platform and all-Git execution, measured resource envelope, WAN, CUI/FIPS claims: HOLD / not established by this review. Known functional incompleteness is not relabeled as a discovered privacy exploit, and this source PASS must not close those delivery gates.
