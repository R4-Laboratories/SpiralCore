## Blocking finding: a new append can forget already-published debt

**[P1] `installed_owner/retained_telemetry.rs:215–220,280–282`, paired with `installed_retained.rs::prepare_state`.** `retained_catalog` unconditionally interprets missing catalog metadata as an empty catalog. The append path does not compare that loaded set with the other actual entries retained by the supervisor's inventory. After scope A is successfully Protected/Bound, loss of the catalog followed by preparation of a different scope B therefore publishes a B-only catalog and returns success, even while A's original reservation, marker and data remain live. This silently loses durable accounting continuity; it is not an idempotent retry or a request to implement restart adoption.

Required focused countercase: prepare A, retain its marker/data/credit, remove only the catalog as a synthetic metadata-loss fault, then prepare B. The operation must refuse/fence and must not replace missing authoritative history with a successful B-only catalog. The original table and all credits must remain held. The live table must validate the complete expected existing record set before append. Across process death, an independently durable denial anchor is also required so loss of the catalog alone cannot be interpreted as a clean zero-debt installation by generic epoch transitions.

Root's proposed bounded monotonic beacon in the already-bound original owner.lock inode is architecturally compatible with the existing object-ID record and Core holder expectations: state.bin's bytes/digest remain unchanged. This is a proposal review only. Any implementation must retain the original descriptor/inode, never truncate/replace it, sync the beacon before the first catalog/marker effect, refuse existing unknown or partial content, and make generic transitions deny **any nonempty** beacon, even malformed. It supplies denial only, never admission or exit proof. Clearing is outside the current authority. No guarantee against hostile same-UID truncation of authoritative files is inferred.

## Records descriptor precondition before binding/producer activation

`bind_files` checks identities, mode, links and size, but accepts a write-only records File. `seal_after_endpoint` later calls `FileExt::read_at` on that retained handle. A nonempty write-only records File necessarily fails that read with EBADF after an otherwise valid receipt. Canonical `CappedJsonlSink::create` currently opens append-only without read access; the future strict preopen/Sink::over path must therefore open read+append (or retain an independently verified readable original handle). Enforce the records-access precondition before committing Bound. Root has acknowledged it. No actual sealed-receipt execution or producer failure was claimed by this review; producer composition remains pending.
