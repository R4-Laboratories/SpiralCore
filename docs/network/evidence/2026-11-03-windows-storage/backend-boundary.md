# Win32 backend boundary correction

The complete native Windows build rejected the original filesystem module under the transfer crate's `#![forbid(unsafe_code)]`. The correction preserves that prohibition byte-for-byte and extracts the reviewed implementation to `crates/spiralcore-storage-windows`. This independent crate contains only `std` and pinned `windows-sys = 0.61.2`, enables `deny(unsafe_op_in_unsafe_fn)`, and exports safe private-file operations. It contains no MVM dependency, codec, protocol, authority model or alternate object store.

The safe interface is `private_file`, `private_dir`, `open_read`, `create_new_file`, `open_owner`, `publish`, `sync_existing` and `remove_stage`. Its `Storage`, `Unsupported` and `Limit` errors map exhaustively to existing transfer errors; `Limit` preserves the original-path length refusal. The outer Windows module is a safe mapping only. The FFI extraction changes visibility, not filesystem behavior. ACL/junction mutation tests now exercise the backend directly. The transfer crate retains three portable integration tests and its Windows path-alias integration test. Expected native nonzero scopes are Unix outer three, Windows outer four and Windows backend two; report them separately.

Intermediate checks are in `validation/backend-separation-first.*` and `validation/fixture-unique-first.*`: the exact backend and both Windows test bodies passed MSVC-target Clippy with warnings denied; the three portable integration tests passed on native Linux. MSVC cross-compilation is not Windows execution. Native Windows runtime qualification of the extraction and safe outer mapping remains pending a new hosted attempt. No macOS build, VM or performance measurement ran for this correction. `validation/backend-extraction-source.sha256` pins all ten changed or directly relevant source/lock files.
