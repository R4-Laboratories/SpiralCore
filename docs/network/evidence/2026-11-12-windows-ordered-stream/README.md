# Windows ordered FlowMux stream

The original 240-second gate expired on both instrumented Windows x64 runners. Server 2025 had acknowledged and recovered 3,710 of 4,096 blocks in each direction. Server 2022 had acknowledged 3,653 and 3,652, with matching opposite reads. All completed blocks passed exact 16 KiB comparison. The two receivers retained 64 publications each; both authorization scopes still passed. The Server 2022 sampler recorded zero waits over its 1.25-second reporting threshold. The later read timeout and EOF occurred after the original gate fired. [Server 2025 timing run](https://github.com/R4-Laboratories/SpiralCore/actions/runs/43294727888/job/131449905157) · [Server 2022 stall run](https://github.com/R4-Laboratories/SpiralCore/actions/runs/43294727888/job/131449905478)

On the same tested Git tree, ordinary Server 2025 completed in 204.890 s using 77.250 s of process CPU, and ordinary Server 2022 in 153.087 s using 107.594 s. Both peers read back 67,108,864 bytes in each direction. Peer A sent 5,395,050 TLS bytes and received 5,395,015, matching peer B. Each run used its own hosted machine. These samples cannot isolate the cost of instrumentation or predict a repeatable deadline margin. [Ordinary native suite](https://github.com/R4-Laboratories/SpiralCore/actions/runs/43294727966) · [Scoped measurements and log hashes](baseline.json)

The timed Server 2025 receivers spent 111.53 s and 111.61 s handling Commit, compared with 22.15 s and 23.34 s handling Begin. These are overlapping wall intervals. In three separate 128-block local filesystem controls, flushing staged file data took 1.261–1.369 s, and write-through namespace publication took 0.752–0.785 s. Both quota scans together took 0.445–0.453 s. The samples identify durable publication as a substantial cost. They do not establish which filesystem operation determined latency on a different host. [Per-stage measurements](baseline.json)

In the application delivery path, an ordered receiver reopened the newly committed publication to verify bytes and record its charge, discarded the verified bytes, then performed another full read for local delivery. A focused control observed two full reads. The candidate passes the first verified readback directly to that application turn after its ledger and authority checks. A later independent read or replay still reopens storage. Corruption between the original delivery and a replay causes a refusal. The durable file flush, write-through rename, quota scans, eviction policy, TLS protocol and deadlines keep their existing behavior. Native Windows acceptance on the candidate requires the unchanged full workload. [FlowMux tracker](https://github.com/R4-Laboratories/SpiralCore/issues/44)
