# Firecracker activation and original retirement

Trial 7 booted the same signed 61,860,864-byte application package as the [first six trials](README.md). The corrected MVM SDK and host helpers activated the original guest. The controller published the guest and host public-key observation from its admitted endpoint. The guest console recorded the unprivileged egress client starting and its proxy listening on loopback. The SDK accepted the launch 33.193 seconds after the controller started preparation, including 6.283 seconds of preparation. [Measurements, executable identities and log digests](activation-only.json)

The witness then waited 40 seconds for a detached workload exit. It never sent the guest agent’s separate `RunEntrypoint` request. The wait returned an unknown exit code, the cooperating peer accepted no caller within its 90-second deadline, and the retired workload audit file was empty. The console also recorded a rejected control-frame read, with no evidence identifying that read as a workload request. No application readback, host egress verdict, transfer cost or traffic measurement was obtained.

The SDK collected the original guest and the tenant helper stopped. The resource snapshot showed zero guests, guest RAM and workers. It retained 806,371,328 host metadata bytes, 9,494,528 cache bytes and 536,875,008 staging bytes. This witness returned the workload error before its final four-reservation identity assertion. Its private mount and loop attachment were gone after collection. The SDK command and its collected children consumed 31.58 s user and 1.84 s system CPU over 73.57 s wall time. The controller reported a 768,244 KiB virtual peak and 271,232 KiB resident peak. The external peer occupied 90.05 s wall time.

The next workload invocation must use the original admitted guest agent's bounded entrypoint call, collect its terminal event, verify the two guest reports and compare them with the cooperating peer and signed host audit.
